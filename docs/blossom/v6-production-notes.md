# 0.4 制作复盘：从实际故障留下的工程经验

本页记录这一轮实现、实景检验和交付工具审阅中确实发生的问题。文档中的实验结果各有范围：独立花卉实验不代替整场游戏，CPU 用例不代替普通输入实玩，旧候选的反例不改写为新候选的通过。最终发布状态以发布清单和与其一致的报告为准。

## 1. 跟随镜头不能同时改写玩家正在使用的移动基准

问题来自一个反馈环：按住横移时按当前镜头角计算移动，镜头又追随角色刚产生的朝向；下一帧移动方向随镜头旋转，角色因此不断改变方向。单独看“相对镜头移动”或“跟随角色”都合理，组合后可能绕圈。

当前 `createTravelController` 在按键方向组合改变时确定移动基准；同一段持续输入保持这条方向，镜头依据实际位移缓慢追随。主动环看会重新设定基准，并保留 1.8 秒手动控制窗口；静止和专注交互时不强行转回，C 则是明确的回正意图。轻缓动态另有转速限制。

证据：[navigation.js](../../spring-letter/src/navigation.js)、[跟随镜头用例](../../spring-letter/tests/travel-camera.test.js)。其中持续横移用例同时推进运动和转镜头，要求轨迹保持直线；这比只检查一次角度计算更能覆盖原问题。CPU 轨迹成立不等于所有用户都觉得舒服，实际视角和遮挡仍需实玩检查。

## 2. 花体与粒子要共享可追溯的源，而不是每次换装重新撒点

四种花形的实体与粒子使用同一套生成几何；闭合与开放形态通过同一三角形及重心坐标采样，保持点的对应关系。花瓣、枝叶、花心的取色域分开，再共享视觉系列的配色。这样才有“这一朵花散开，又回到这一朵花”的身份连续性。

同数量换花形时，`setSource` 更新目标位置和颜色，保留当前模拟位置、速度及资源；换色仅更新颜色。改变质量档位时按稳定线性点编号保留重合部分，避免按归一化纹理坐标重新配对导致画面洗牌。旧资源在需要重建时明确释放。

[隔离实验报告](../../spring-letter/evidence/v6-flower-lab/report.json)记录换色位置误差、换源位置与速度误差均为 0，归形误差约 `5.59e-7`，值均有限；30 轮实际绘制的资源计数维持 17 个几何与 22 个纹理。此结果只覆盖该实验场景，不能宣布全游戏无泄漏。早先一份隐藏花体的资源观察被保留为范围不足的历史记录，之后改为花体实际可见再绘制，防止“对象未进入渲染”制造虚假的稳定。

实现入口：[botany.js](../../spring-letter/src/botany.js)、[particles.js](../../spring-letter/src/particles.js)、[flower-presets.js](../../spring-letter/src/flower-presets.js)。

## 3. 首次可见时才编译的程序，会把卡顿留给第一下互动

首次打散的隔离实验出现 801 ms 的 RAF 间隔。原因排查指向首次可见粒子程序及透明花材质路径：只准备一个不透明实体，不能保证另一种渲染状态已经建立。加载完成后才暴露这条路径，会让用户把编译停顿理解成手势没有反应。

随后在加载阶段实际绘制透明花体和可见粒子。对照实验中的预热耗时为 482.3 ms，进入互动后的最大 RAF 间隔为 49.9 ms。两次都是独立实验页的新浏览器上下文，没有清除显卡驱动缓存，也没有主世界、完整后处理，因此不能作为本版全游戏冷启动性能承诺。

证据：[首次破开](../../spring-letter/evidence/v6-flower-first-break-timing.json)、[预热对照](../../spring-letter/evidence/v6-flower-first-break-prewarmed.json)。主程序进一步预热了不同材质和粒子、反射、合成路径，并恢复原花型、系列、透明度、可见性等状态；预热不调用玩家关卡进度。结果应分别报告加载时间、首交互间隔与稳定运行区间，平均帧率无法替代这三项。

后续 F 候选改为在后处理实际使用的目标上预编译，并在成功或异常时恢复原目标；它解决的是重复生成用不到的着色器变体。具体的独立对照、舍弃方案与正式候选身份另见[启动预热优化](v6-startup-optimization.md)，不与上面的早期花卉实验合并统计。

## 4. 有存档不等于字段完整，空值也不是默认参数

新增跟随镜头、花型、材质偏好后，旧存档可能完全没有这些字段。偏好还可能是 JSON `null`、错误类型或损坏文本。默认函数参数只处理 `undefined`，不能假设解析成功就得到一个完整对象。

当前恢复流程先创建完整默认状态，再逐字段接收合法布尔值与枚举；偏好读取使用可空访问并兼容旧旅程中的 settings。画面密度、轻缓动态、静音和衣橱偏好单独保存，开始新旅程不会重置用户的体验选择。封面阶段也应用已保存花型与材质，避免存储正确但要进游戏后才生效。

证据：[preferences.js](../../spring-letter/src/preferences.js)、[game-model.js](../../spring-letter/src/game-model.js)、[偏好用例](../../spring-letter/tests/preferences.test.js)、[存档恢复用例](../../spring-letter/tests/model.test.js)。这些用例分别覆盖偏好与旅程分离、旧字段迁移、坏设置和无效存档；没有将“格式能解析”当成“内容可使用”。

## 5. 自动归形是世界进度，不应依赖面板仍打开

D 候选发现了真实边缘问题：玩家已经破开并写过足够的风，随后离开近看；花在世界里自然复原，但关卡完成判断只在花卉专注状态调用。于是必须重新靠近一次才能解锁。视觉生命周期已结束，任务生命周期却漏掉了这个时刻。

修正后，主线运行期间持续观察花的归形阶段；新的写风进度仍只在靠近花时累计。这样离开不会丢失完成，也不能在远处随意挥动画笔刷过教学。暂停时两种时序均冻结；模拟步长与演出生命周期时间分开处理，低帧率下不能因为物理步长截断而把“等待片刻”拉长成另一种节奏。

证据保留了前后两个版本：[D 候选反例](../../spring-letter/evidence/v6-candidate-d/v6-flower-leave-before-return.json)的 `solvedWithoutReentry` 为 false；[E 候选普通输入回归归档](../../spring-letter/evidence/v6-candidate-e/v6-flower-leave-fixed.json)在 08:36:31 UTC 记录 `regression passed`，该值为 true，入口为 `index-Cl_BoOsu.js`。另有[调用层集成用例](../../spring-letter/tests/flower-return-integration.test.js)验证离场完成只触发一次，以及远处手势不能累计未学会的花课。不能用 E 的修复结论覆盖 D 的反例文件，也不把 E 归档标作后续 F 候选的回归。

## 6. 压力观察首先要证明看到了新帧

工具审阅发现 `array.slice(-count)` 在 `count === 0` 时等于 `slice(0)`，会把旧缓冲区整段取出。若浏览器没有产生新帧，测试仍可能拿到很多旧帧并宣布样本充足。修正后的采样器先检查帧计数递增，再只取新增窗口；空样本、计数倒退、非有限间隔都直接失败，稳定阶段还要求足够的新样本。

另一处问题是只检查最后三轮资源的最大最小差。每轮泄漏一个对象时，尾部差值始终很小；运行越久，遗漏越严重。现在先运行完整暖机轮，再固定基线，检查每个匹配阶段的几何、纹理与程序计数，同时检查缓慢单调增长和连续增长趋势。合理抖动与新增资源路径需要分析，不能任意移动基线抹掉增长。

证据：[v6-soak.cjs](../../spring-letter/scripts/v6-soak.cjs)、[工具反例与回归用例](../../spring-letter/tests/v6-tooling.test.js)。本轮新增的 6 个 CPU 用例通过，覆盖零新帧、有效窗口、稳定平台、渐增泄漏、缺项计数，以及页面错误和 console.error 的收集。它们验证观察工具的逻辑，不等于完成 45 分钟压力实跑，更不是显存泄漏证明。

## 7. 交付证据必须绑定同一份 JS、CSS 和文件集合

多代理并行调整时，Vite 热更新曾干扰正在进行的实玩。之后先冻结运行源，构建独立候选，再让验证只访问该候选；艺术实验页与主游戏证据也分别归档。候选不是文件夹名字，而是一组可核对的字节。

交付工具审阅还找到几处可能假通过的路径：报告的 CSS 字段形状不同而漏查；录像只看检查列表却忽略 `success`；压缩包与自己内嵌的旧清单一致，却没有与当前发布清单一致。修正后的门槛同时核对入口 JS、CSS、前后构建状态、源文件和 dist 的 SHA-256；录像核对成功状态、实际字节数与 SHA；解压包必须匹配当前 release manifest 的版本、构建与完整文件集合，再实际通过 HTTP 读取并校验文件。

证据：[发布门槛](../../spring-letter/scripts/release-v6.cjs)、[实际解压与服务验证](../../spring-letter/scripts/verify-v6-package.py)、[打包验证 CPU 用例](../../spring-letter/tests/v6-package-tooling.test.py)。打包校验的 3 个 CPU 用例分别接受一致的新候选，拒绝内部自洽但已过时的候选，以及 CSS、版本或文件集合不符的包。界面检验同时记录 pageerror 与 console.error，避免着色器错误只进控制台而漏报。

这些门槛的作用是让“测试过”与“交付了”指向同一对象。它们不使画面自动更好，也不代替玩法判断。艺术上还未达到的部分单列于[视觉边界复核](v6-visual-boundaries.md)，已实现故事和交互以[可执行脚本](v6-play-script.md)为准。
