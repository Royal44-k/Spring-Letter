# 花漾年华：待寄出的春信 0.6 · 产品与试玩档案

记录日期：2026-11-21。本档案对应已本地交付的“来信之庭”0.6.0，来源为冻结构建 **release-d**。本机 5192 已更新，桌面与浏览器静态包已生成并核验。它不是外网上架公告、销售预测或商业成熟认证；没有招募、联系玩家或收取费用。

## 一句话介绍

**把花打散成风，接通三座庭院的叶脉，再决定把春天先留给谁。**

这是一段以自然观察、空间解谜和回信选择组成的单人艺术探索旅途。你扮演新醒来的送春者弥，走进保存故乡季节的方舟，替远行的人处理那些还没有等到回应的小事。核心体验是观察来信、试转叶脉石、看见花尘抵达、留下照料和回信。追风、风笔和旧物支线提供不同节奏，不是主线前必须刷完的清单。

桌面浏览器是首先服务的平台。一次旅程约 20 分钟是设计目标，尚未经过陌生玩家计时验证。风格化实时庭院、程序花卉和采样乐器是当前制作方式；没有真人表演、人物语音、长篇开放世界或经过验证的 AAA 制作水准。

## 为什么值得玩下去

这三个问题需要在真实试玩中成立，才能讨论产品吸引力：

1. **我的动作有结果。** 石上的沟槽朝向决定花尘能走到哪里；老树、新芽、灯、帆和花铃是具体的接受者。接通先展示，确认才记入回信。
2. **下一处需要我换一种想法。** 雨庭教分流；风庭要求绕开会漏风的旧井；潮庭要两路同时抵达。输入方法不变，空间条件逐步增加。
3. **结尾认得我做过的事。** 三庭照料会写进来信册和寄出时的快照，两枚种核还有三种用途可选。回到此前的庭院，可以尝试另一种安排。

两种照料之间的取舍，是“我现在先顾哪一处”：一瓢水、一夜风、一段声音无法同时给所有愿望同样的优先级。它们没有善恶排名，也不通过强弱奖励诱导玩家选所谓正确答案。三庭选择可回访重选；已获得的行路能力不会重复叠加。

## 已进入代码的旅程

以下以 `src/letter-model.js`、`src/letter-controller.js`、`src/game-model.js`、`src/story-content.js` 及相关呈现为依据。实现存在不等于所有设备已经通过验收。

| 阶段 | 玩家做什么 | 生活含义 | 带向下一程的变化 |
|---|---|---|---|
| 初到方舟 | 可跳过的开场介绍弥与旧记录，向第一封信走去 | 弥有照料花庭的能力，没有旧人的记忆 | 以一件可亲手处理的小事进入世界 |
| 雨庭 · 一瓢水的去处 | 转动三块叶脉石，将雨接给老树或新芽 | 禾会在回来后接手另一处；你先替她照料眼前的一处 | 踏风气息恢复更快，下一程开放 |
| 风庭 · 夜渡之前 | 调整叉路，避开漏风旧井，抵达迎客灯或护种帆 | 阿渡希望来客与幼种都平安度过这一夜 | 已完成的庭院之间可以往返 |
| 潮庭 · 留给下一声 | 把两处泉眼汇入同一个收信端 | 可以陪旧曲唱完，也可以为游絮自己的回应留一拍 | 金色花灵的下一次开放有可见预告 |
| 花桥与终庭 | 亲手连桥，携带两枚种核，在旧灯、新芽、远航中安排两处 | 春天既可以陪伴记忆，也可以生长或出发 | 先预览，再寄出带有实际三庭照料的春信 |
| 回来之后 | 续写存档，重看回信，选择漫游或再试一程追风 | 结尾不是把所有未做之事判为失败 | 保留已获得的选择与旅途 |

角色关系有明确边界：弥是新生命；游絮有自己的步调；岑是旧记录里的守园人，当前没有和玩家实时对话。禾与阿渡留下的是旧来信，雨庭、风庭的文字是弥写给他们的回信，不能把它演成已经收到对方即时回答。

### 本轮复核后补齐的交接

- 首屏保留直接点石提示；手机共同标题区提供寄信人与一句愿望，以及展开原文的入口。桌面来信摘要不再只有“展开来信”四字。
- 三庭回信后显示回信首句和具体下一程按钮。按钮收起信纸、设定目标，不替玩家走路或解谜。潮庭完成后沿真实陆路引向旧石台，再提示写风织桥；来信册也能明确追踪已经回过信的庭院。
- 风庭奖励改用“这阵风记住了来路”的中性缘由，不再把点灯写成已经修帆。两种照料的行路能力仍相同。
- 潮庭两种声音已分出确定性的节拍：旧曲的两声部同拍回应，新声让竖琴迟半拍回答。事件区别已实装，是否能被玩家自然听懂仍待听审与陌生玩家测试。
- 角色增加织纹、衣料与邮袋细节；草地/石路脚步随地面变化，短促但有意的移动也能触发第一步，不必长按才有声音。
- “明信片”将当前游戏画面与玩家已经确认的三庭照料组合为本地 PNG；已寄出的春信使用寄出时的快照。不需要账号，也不会自动上传或分享。
- 浏览器无法保存时提供明确的临时旅途入口，保留原存储，显示“关闭页面前请导出”的提醒。临时模式只在当前页面内保存，不能把刷新或关页后仍能续玩当作承诺。

上述是实现状态。与首次审阅的差异及最终待查点见 [产品复核的修复进度](v8-product-audit.md)。

## 为谁设计

这里是招募假设，没有真实用户画像、用户规模或留存数据。

| 首批动机 | 想得到的体验 | 本作必须做到 |
|---|---|---|
| 喜欢艺术探索与短篇叙事 | 一次坐下，走完一段有情绪的旅途 | 世界有生活痕迹，目标明确，音画与行动相互回应 |
| 喜欢温柔空间解谜 | 看懂关系，亲手试出答案 | 流向清楚，失败可理解，撤销/提示可达，无必需的手速考验 |
| 喜欢留下个人作品 | 一封能认出自己选择的信 | 结尾准确引用真实安排，可以重看和保留 |

高速竞技、长线数值养成和强战斗不是本章节当前的主要承诺。后续内容应优先增加新的空间条件、人物愿望和场景回应，而不是把相同回路换颜色后称作新关卡。

## 声画与免费素材

花型、花色、粒子规则、叶脉石、场景结构、人物与界面由项目程序化制作。主花可以散成随花色变化的花尘、受到风笔牵引并自动归形。庭院来源花也有绽放、散开、沿接通路径流动与归形的过程。四种花形与五个系列仍可选择。弥的织纹与邮袋细节服务于送春者身份；这些仍是风格化实时角色，不能称为真人级表演。

当前源码配乐使用 VSCO 2 Community Edition 的免费 CC0 真实乐器采样，由项目编写旋律、和声与情境调度。三庭有不同的音乐速度与配器回应；转石、接通和回信有声音反馈。潮庭的“旧曲 / 新声”以同拍回应和迟半拍回答区分，避免只有文字变化。

release-c 已接入 Kenney 的草地与混凝土地面脚步、短采矿敲击，以及 isaiah658 的鸟鸣、Thimras / Eike Germann 的河流实录，均为 CC0，release-d 保留同样的声音。游戏把混凝土脚步用于石路，把短敲击用于转片触碰；不把它们的原始录音误称为自然石材或实际机关录音。鸟与河声各为处理后的 20 秒循环，随情景低声混入。素材来源、原件与处理后哈希见 [素材清单](../../spring-letter/ASSET_SOURCES.md)。没有人物配音，也没有声称人工试听。

### release-d 实际混音记录

已归档 [录制记录](../../spring-letter/evidence/v8-audio/captures/2026-11-21T04-13-29-998Z/capture.json) 与 [完整音频分析](../../spring-letter/evidence/v8-audio/captures/2026-11-21T04-13-29-998Z/actual-analysis.md)：录制路线检查 37/37，解码与分析检查 10/10，均对应 `index-DTQylXTU.js`。普通输入触发首次音频、短按/持续脚步、雨庭转石/回信、花尘/风笔、静音与暂停，没有直接调用游戏内部音频 API。

全量有效 PCM 为 96.660 秒；媒体跨度 100.582 秒，暂停期间存在无音频包区间，不能把两种时长混为一谈。解码样本峰值为 −6.34 dBFS，RMS 为 −24.01 dBFS，达到幅度 1.0 的削波样本为 0。稳定静音保护区峰值 −115.08 dBFS、RMS −143.13 dBFS；固定 3 个持续音源、16 个常驻节点。RMS 不是 LUFS，样本峰值不是过采样 true peak，统计不证明音乐好听或设备平衡。

产品页 [约 76 秒的实录片段](media/v8/game-audio.mp3) 从录音起点截至 flower-rest 标记，原增益、无归一化或拼曲，文件 1,828,268 字节。它包含初庭、草地/石路脚步、雨庭转石与树的回信、花尘与风笔；**不包含可选追风或潮庭 old/new 两种回应**，不得把它当作这两个功能的听感证明。潮庭差异目前由编曲/调度测试覆盖，人工听审与真实设备听感仍未进行。

已登记的外部环境资产来自 Poly Haven 的 CC0 HDR、岩石、石膏和路面贴图；软件依赖另有 MIT/Apache 等许可。完整作者、来源、处理记录和许可证见 [素材来源](../../spring-letter/ASSET_SOURCES.md)。免费指没有素材采购、付费生成接口或付费服务依赖，不意味着设备和开发时间没有成本。

参考作品仅用于观察设计方法，不能把商业游戏截图、音乐、角色或网站资产直接放进发行包。研究与采用必须分开记录。已有一手案例的判断与链接见 [产品研究](v8-product-research.md)，用户所提射击案例的事实边界见 [案例核查](fps-case-v3.md)。

## 8–12 人小样本试玩方案

这是供项目持有人使用的招募和观察方案，尚未执行。样本用于找阻塞与解释体验，不具统计代表性。目标是同时纳入熟悉艺术探索/温柔解谜的人，以及不熟悉 WASD 的轻度玩家；不要只找了解项目开发过程的朋友。

### 可直接使用的招募文案

> 我们在做一段关于照料庭院与回信的独立游戏，想请你试一段尚在打磨的章节。你会转动石上的叶脉，让花尘抵达不同的花池，也可以慢慢探索。测试约预留 30–40 分钟，其中游玩长度尚在验证。无需付费或注册；可以随时停止。我们想知道你真实遇到的困惑，不需要夸奖作品。默认不录音录像；如希望记录画面，会先单独征求同意。

招募说明应告知运行条件与测试版性质。联络与同意记录由组织者自行管理，不能把个人身份写入游戏反馈文件。默认由观察者记关键事件，录屏不是参与条件。

### 主持脚本

1. **开始前（约 2 分钟）**：“你平常会玩什么样的游戏？最近一次用键盘移动人物是什么时候？”说明可以随时停、不需要答对、不评判操作能力。给一句产品介绍与入口，不提前讲解答案。
2. **开始后（静默观察）**：记录第一次可操作、第一次有效转石、首次接通和首次主动回信的时间。两分钟时问一次：“你觉得现在可以做什么？”不要问带有正确答案的“你是不是要修好三庭”。
3. **遇到卡顿或迷失**：先问“你现在在找什么？”只记录，不立即指路。玩家主动求助时，先提醒游戏内提示入口；仍无法继续才给一次必要帮助，记录时间和具体话语。不要把帮助后的通过记作独立完成。
4. **首庭之后**：“接下来你可以继续，也可以停在这里，两个选择都可以。”记录行为和原因，不用这一次选择计算产品留存率。
5. **结束后（约 5–8 分钟）**：“哪一处最想再停一会儿？”“第二庭和第一庭有什么不同？”“能指给我看一个你改变的地方吗？”“哪一刻想退出？”“看介绍时想象的体验，与实际有什么差别？”先留原话，再归因。
6. **可选反馈文件**：玩家自己在设置或结尾打开“留下试玩感受”。填完先预览，再决定是否下载及另行分享。取消不会影响游戏；主持者不得替玩家选择答案。

### 事件记录模板

| 项目 | 记录内容 |
|---|---|
| 匿名编号与自述经验 | 例如 P01；键鼠经验与相关游戏经验，不记录姓名或联系方式 |
| 运行环境 | 经玩家同意记设备大类、浏览器、画质；不要把硬件序列号、IP 或账号作为测试字段 |
| 关键时间 | 可操作 / 首次有效转石 / 首庭接通 / 首次回信 / 停止 / 是否到结尾 |
| 求助与阻塞 | 所在位置、原话、重复操作、是否打开提示、主持者如何干预 |
| 体验原话 | 喜欢 / 无聊 / 困惑 / 听感 / 选择记忆；尽量保留原句 |
| 结束结果 | 自行停止或走完；停止原因；导出反馈是否自愿提供 |

### 本次团队决策阈值

以下数值是**事先拟定的内部目标，不是行业基准**。8–12 人样本不适合对微小比例差异下结论。用人数和原话报告，若不是 10 人，应报告实际人数与分母，不套写“8/10”。

| 问题 | 预设目标（以 10 人作示意） | 未达到时的优先动作 |
|---|---|---|
| 目标是否被理解 | 至少 8 人两分钟后能说出照料庭院/回信的意图 | 改第一镜头、目标物与当前行动，先不增加长说明 |
| 第一庭是否能独立完成 | 至少 8 人在进入机关后 4 分钟内回信，无口头教答案 | 查操作入口、流向、断点、确认；不要直接自动解题 |
| 后庭是否有新思考 | 至少 7 人能描述止漏或两路汇合的差别 | 改条件与反馈，不靠更多转子制造长度 |
| 选择是否被记住 | 至少 7 人能指认一处自己照料过的对象或对应回信 | 强化环境变化及具体文字，减少泛化诗句 |
| 是否存在基础阻塞 | 两名及以上在同一基础动作卡住，或任一人遇到丢档/无法退出 | 立即优先处理，不用平均满意度抵消 |
| 是否有继续意愿 | 记录人数与理由，允许“不确定/暂时不” | 按玩法、性能、方向、审美分开处理；不是购买转化 |

不建议本轮用 NPS、付费转化率或 7 日留存作漂亮数字。先证明陌生人能自行理解、继续和完成，再决定扩大样本。

## 从本地候选到商业项目

### 第一阶段：可信的免费试玩

本轮的合理目标是一个可审查、可恢复进度、来源清楚的章节样本，以及一份能帮助做产品判断的反馈资料。入口无账号、无内购、无广告 SDK；游戏反馈只经玩家确认下载本地 JSON，不上传。明信片由玩家点击后导出 PNG，也不会自动分享。首次启动仍需要浏览器与本地 HTTP 服务；不把本机地址称作外网可分享网址。临时旅途是存储受限时的明确降级，玩家应在关闭页面前导出存档，不能拿它替代持久保存。

允许对外主张的内容应限于实测可玩的系统与真实游戏画面。若将来发布免费静态试玩，可研究 itch.io 的 [HTML5 规则](https://itch.io/docs/creators/html5)；当前未发布、未建立收款。Steam Playtest 与 Demo 是后续有相应开发者资格后再评估的渠道，不能当作已经取得的免费发行能力。

### 第二阶段：验证扩展是否值得

先修复盲测反复出现的问题，再测试一段新的庭院机制是否仍能带来兴趣。拟议完整版可以是单次购买、内容完整的短篇；章节数量、售价与日期仍待制作成本、内容密度和玩家意愿共同决定。不要在内容和设备条件不明确时询问抽象的“你愿意付多少钱”，也不要把点赞计为购买。

商业决策至少需要分别回答：谁会主动玩、为什么愿意继续、能否被可信地展示、每新增一段内容需要多少制作与维护成本、可达渠道有哪些具体限制。它们都不是本轮代码自动测试能替代的证据。
