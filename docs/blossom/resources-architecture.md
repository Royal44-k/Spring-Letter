调研日期：2026-11-18。范围：只读审查现有工程、核对官方资源及示例、提出可执行的技术方案；本次没有下载制作素材、调用收费生成服务、采购、改动游戏代码或运行新原型。本文的预算是待实测的设计目标，不是已达到的性能。

用户已明确新作是独立主题，与金沙项目无关。浏览器只是本报告建议的首个交付平台，尚不是用户确认的平台选择。文中的花、种子、风场及空间机关是技术载体示例，不替代最终创意方案。

2026-11-18设计深化补记：本报告保留技术与许可依据；新的统一聚焦输入、临时结构可回收规则、两核三用途与叙事状态，以[主设计v2](design-proposal.md)和[体验蓝图](experience-blueprint.md)为准。新增远景/记忆片段仍受同一性能预算约束，不自动获得更多粒子、透射层或首包容量。

## 1. 建议与适用边界

主任务的逐帧观察摘要指出：花朵参考是明亮水面展场中的百合，有液态银、雕塑晶体、自然粉白/金色三种材质观感，支持花开程度、绕视、水面交互、追光、自动旋转与昼夜；粒子参考是暗背景密集表面点云，上粉下蓝，指针局部排斥、旋转和缩放。其“240K”是画面文字，未以运行计数核实；全屏扩张也可能包含镜头缩放，不能直接称为已证实的形态溶解。本报告没有独立重放视频，以上采用主任务提供的观察结果。

因此建议的空间方向是**明亮水面花庭/展场与深色粒子空间之间的可探索过渡**，不是森林换皮。先做一个有完整玩法因果的短段落：玩家激起水纹、改变光的位置或作用场，让同一批粒子从花朵脱离、穿越空间、重新形成可识别的形态，并因此打开新路径。连续分解—重组属于新作的设计提案，不冒充视频已经证明的机制。近景花瓣需要真实三维曲面和侧光；中景以连续粒子运动表达变化；水台、可行走表面与远景建立空间尺度。美术的主要投入放在原创主花、材质、构图和运动节奏，免费资源只补充需要的部分。

若优先“发链接即可体验”，可提议 Three.js + Vite 浏览器方案。第一版以 WebGL2、GPU 纹理模拟和受控的后处理为主，保留无状态顶点着色器形变降级。WebGPU + TSL 值得另做能力样机，但应先验证目标设备，再决定是否把整套材质及后处理迁过去。官方当前仍将 `WebGPURenderer` 标为实验性；其自动 WebGL2 回退并不意味着旧 `ShaderMaterial`、`onBeforeCompile()` 和 `EffectComposer` 可以原样沿用。[Three.js WebGPURenderer 指南](https://threejs.org/manual/pages/webgpurenderer)

若最终选择桌面原生游戏，可评估 Godot：它提供 `GPUParticles3D`、粒子处理材质和粒子着色器。Godot 的网页导出只支持 WebGL2 Compatibility，不能把桌面 Forward+/Mobile 特效直接视作网页能力；当前官方文档亦说明尚不支持 WebGPU。故它是另一条产品路线，不是免费获得网页电影级渲染的捷径。[Godot 粒子节点](https://docs.godotengine.org/en/stable/classes/class_gpuparticles3d.html)、[Godot 网页导出](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)

### Blender 制作链

采用原创曲线/网格制作花瓣，保留 `petalId`、花瓣内 UV、法线、顶点颜色/权重与统一尺度；输出游戏网格、粒子目标采样和少量烘焙贴图。材质复杂节点需在目标渲染器中重建或烘焙，不能把 Blender 离线渲染效果当作浏览器自动得到的效果。GLTFLoader 支持 glTF 2.0 以及 Meshopt/Draco、BasisU 等对应扩展，但需要接入对应解码器。[GLTFLoader](https://threejs.org/docs/pages/GLTFLoader.html)

运行资源推荐 GLB + 必要纹理 + 二进制目标点表。对适合的贴图使用 KTX2/Basis；KTX2Loader 必须先检测目标设备压缩纹理支持，再转码为该 GPU 可用格式。[KTX2Loader](https://threejs.org/docs/pages/KTX2Loader.html)

素材登记至少包含：资产名、具体页面、作者、下载日期、许可及原文链接、下载文件与校验值、加工内容、成品路径、强制署名要求。CC0 虽不要求署名，仍保留内部出处以便维护。

## 4. 粒子主体：统一身份、形态与空间

以下为针对本项目提出的实现设计，不是声称官方例子已经提供完整游戏。

### 4.1 三层表现，避免整个世界都是发光点

1. **近景结构层**：真实曲面花瓣、花芯和少量露珠。花瓣有曲率、厚薄与法线；少量实例组成可读轮廓，运动时保持空间遮挡和侧光。
2. **主体粒子层**：承担花瓣分解、粒子流、重组和玩家风场响应。采用 GPU 位置/速度状态和可变目标，而非每粒子一个 Object3D。
3. **环境层**：浅水展台、可行走平台、明亮空间边界或暗场远景轮廓、少量浮尘。让玩家可以判断距离、行进方向和世界变化；黑背景不能代替可读的空间。

对相同几何与材质的花瓣/种子使用实例化减少绘制调用；细小粒子可用 Points 或实例化面片，较大有转向要求的花瓣用低面数网格。实例化降低 draw calls，但不会自动消除透明重叠的像素成本。[InstancedMesh](https://threejs.org/docs/pages/InstancedMesh.html)

### 4.2 固定粒子身份与数据

为每个粒子保留稳定 `id`，不要在场景切换或每帧重新随机生成。数据建议分为：

| 数据 | 内容 | 更新时机 |
|---|---|---|
| 不变元数据 | seed、分组/花瓣 ID、颜色参数、大小、相位、法线或朝向参数 | 构建/载入时一次 |
| 当前状态 | `position.xyz`、`velocity.xyz`，剩余通道可存寿命/状态权重 | GPU 固定步长更新 |
| 目标形态 | A/B 各一份等数量的目标位置，必要时目标法线 | 形态预加载时；不要每帧上传 |
| 玩法控制 | 当前形态、进度、风场方向、少数吸引点、玩家位置、解谜阶段 | CPU 每帧仅上传少量 uniform |

WebGL 纹理版中，ID 对应纹素中心：`((id % W) + 0.5, floor(id / W) + 0.5) / (W, H)`；数据纹理使用 nearest 采样，关闭 mipmap，避免邻粒子数值混合。稳定身份从索引或完整精度数据取得，不能把大 ID 装进半精度浮点通道后期待整数精确。

离线采样所有目标形态时固定随机种子。官方 MeshSurfaceSampler 支持自定义随机生成器、按面面积采样，以及用权重属性选择采样密度；它只解决采样，不自动解决形态之间好看的对应关系。[MeshSurfaceSampler](https://threejs.org/docs/pages/MeshSurfaceSampler.html)

**对应关系需单独设计**：先按花瓣/花芯分组，再按极角、径向位置或花瓣内 UV 建立一致排列；必要时离线做有容量约束的一对一匹配，避免多个粒子绑定同一终点。随机 A 对随机 B 即使数量一样，也容易得到穿心直线、结团和不稳定轮廓。网格 morphTargets 则适用于已经具有对应顶点的形态，官方例子通过同一顶点序列生成目标；它不是任意模型之间自动变形的工具。[官方 morph 示例源码](https://raw.githubusercontent.com/mrdoob/three.js/r185/examples/webgl_morphtargets.html)

LOD 使用均匀分布的固定 ID 子集或预先排列的多级样本；别按花瓣排序后直接截取前一小段，导致低画质缺少整朵花的一侧。画质切换时保留当前活动 ID 的状态；需要重建更小模拟纹理时，在停靠/形态稳定阶段进行，或提供明确映射。

### 4.3 连续变形与交互力

建议状态图：`停靠形态 → 局部脱离 → 流场输送 → 目标聚合 → 轮廓稳定`，允许玩家提前松开、改变风向和重新尝试。每个阶段改变力和权重，不清空粒子系统。

参考计算：目标点先沿曲线或分组控制点运动，粒子受 `k × (target - position)` 回归力、速度阻尼、局部风/涡旋、少数玩家吸引或排斥点影响。每粒子的脱离时间由固定 seed 与花瓣分组错开。接近重组完成时逐渐减弱噪声，确保轮廓真正收敛；一直叠加大噪声会让终点永远像一团烟。

可用固定步长累积器（例如 1/60 秒）与最大追赶步数，后台恢复时限制累计时间；性能不足时降到 30 Hz 模拟并在渲染中插值。重要：`GPUComputationRenderer.compute()` 的所有变量读取同一旧缓冲；不能因为先注册 velocity，就假定 position 本轮会读到新 velocity。采用显式的旧状态更新，或自行安排分阶段 passes 实现需要的积分顺序。[GPUComputationRenderer 源码](https://github.com/mrdoob/three.js/blob/r185/examples/jsm/misc/GPUComputationRenderer.js)

官方 GPGPU birds 示例可学习状态纹理、双缓冲和交互输入，但它在每粒子的速度计算中遍历其他粒子，源码默认仅 `32 × 32` 个。不能直接把该邻居循环扩至数十万。新作先用 O(N) 的解析风场与少数作用点；只有玩法确实需要粒子互相作用时，才评估空间网格等局部邻域方法。[birds 示例源码](https://raw.githubusercontent.com/mrdoob/three.js/r185/examples/webgl_gpgpu_birds.html)

### 4.4 玩法与模拟解耦

玩法保存“风口方向、种子到达哪个节点、哪些通道开放”等离散事实；GPU 粒子负责可视化与手感。不要每帧把所有粒子位置读回 CPU，也不要让通关依赖数十万粒子的精确碰撞结果。

建议交互范式：玩家在浅水展台间移动、改变光源位置并拨动水纹；花瓣依次张开，接近指针的粒子局部让开，显露可以对齐的形态线索。进阶空间引入有方向的作用场，引导粒子团跨越间隙；聚合成功改变可通过的平台或打开路径。失败时粒子回落到附近可再次尝试的位置，保留因果。判定由 CPU 中少量引导体、触发体和进度模型完成；视觉粒子跟随这些状态。这样降低画质不改变可通关性，静音和减少动态模式也能完成同样任务。

光效、声音、短促震动（平台支持时）与轮廓变化共同提供反馈；不以对白问答或纯点击下一页代替空间行为。镜头自动移动只在短暂发现瞬间使用，控制权及时归还玩家。

## 5. 三条图形路径与真实回退

| 路径 | 技术 | 适用与限制 |
|---|---|---|
| 默认提案 | `WebGLRenderer` + `GPUComputationRenderer` + GLSL + EffectComposer | 与当前本地依赖及常见 WebGL2 实践契合；需检查浮点渲染目标和实际首轮计算 |
| 轻量回退 | WebGL2 顶点 shader 从静态 A/B 点表计算插值、解析风场及有限交互 | 不依赖位置/速度浮点 render target，仍保留三维轮廓与玩法；惯性、持续湍流会简化 |
| 增强评估 | `WebGPURenderer` + TSL 存储数组 + compute + 节点后处理 | 能把模拟保留在 GPU；须完整验证 WebGPU 与强制 WebGL2 回退，不与旧后处理管线混用 |

GPUComputationRenderer 以 RGBA 浮点纹理作为计算变量，每个变量维护两个 render target；可设 FloatType/HalfFloatType。它适合位置/速度双缓冲，但“WebGL2 存在”不是浮点模拟已经成功的证明。[官方 GPUComputationRenderer 文档](https://threejs.org/docs/pages/GPUComputationRenderer.html)

能力选择建议：创建 WebGL2 → 检查相关能力及所用浮点格式 → 做小尺寸 framebuffer 完整性和已知值模拟验证 → 再分配正式规模。`EXT_color_buffer_float` 为 WebGL2 增加 RGBA16F/RGBA32F 等可渲染浮点格式；若缺失或验证失败，进入无状态形变路径，不黑屏。半精度位置采用局部坐标，按视觉精度测试后才替换。[MDN 扩展文档](https://developer.mozilla.org/en-US/docs/Web/API/EXT_color_buffer_float)

无 WebGL2 时显示明确的能力说明和可操作的静态介绍；它不能被宣传为与完整三维游戏等价。处理 context lost、暂停、返回前台、旋转屏幕和内存释放。WebGL 不能可靠查询设备最大显存，应按资源分配估算并保守设预算。[MDN WebGL 最佳实践](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices)

WebGPU 官方 compute particles 展示了 `instancedArray`、`instanceIndex`、GPU 位置/速度和点击作用点。r185 页面文案写“500k”，其源码常量却为 200000；这更说明不能用页面标签推导本作的性能承诺。[固定 r185 示例源码](https://raw.githubusercontent.com/mrdoob/three.js/r185/examples/webgpu_compute_particles.html)

也不应断言“WebGPU 回退完全不能 compute”：r185 的 WebGLBackend 实际通过 transform feedback 实现部分 compute 路径。但 WebGPU 的任意 compute/storage 操作并不因此全部等价，具体着色器、索引、纹理及功能组合仍须在 `forceWebGL: true` 下实测。[r185 WebGLBackend](https://raw.githubusercontent.com/mrdoob/three.js/r185/src/renderers/webgl-fallback/WebGLBackend.js)

## 6. 三种花材、水面与电影感

以下是可实现这些材质观感的技术提案，不是对参考作品源码的反向断言。

| 目标观感 | 建议制作方法 | 验证重点 |
|---|---|---|
| 液态银与薄膜虹彩 | 金属基底、精细 roughness、环境反射；在薄膜区域加入 `iridescence`、`iridescenceIOR` 与厚度变化 | 随视角和灯光变化产生偏色；不要只是给银色花贴固定彩虹渐变 |
| 雕塑晶体 | 有圆润边缘和有限真实厚度的曲面；非金属、`transmission`、`ior`、`thickness`/厚度贴图、吸收颜色/距离；高档才启用少量 `dispersion` | 厚处与薄处、前后表面和底部水面关系可信；不把 alpha 半透明当体积折射 |
| 自然粉白与金色花芯 | 原创百合曲面、花瓣渐变和细纹、控制 roughness/法线、柔和逆光；花芯单独材质 | 微距能看出卷曲与表面细节；没有默认塑料高光，背光近似与真实次表面散射须分清 |

官方参数边界：`iridescence` 表示角度相关薄膜色变；薄膜厚度以纳米计。`transmission` 非零时保持 `opacity=1`；`thickness=0` 表示薄壁，非零按网格坐标尺度描述体积。`dispersion` 仅用于透射对象。物理材质每像素成本较高，需要环境照明支持。[MeshPhysicalMaterial 当前文档](https://threejs.org/docs/pages/MeshPhysicalMaterial.html)

**版本差异必须落到本地实现。** 当前文档已把 `iridescenceThicknessRange` 标为自 r187 起弃用，改为 minimum/maximum 两属性；本机 r185 实际仍使用 `iridescenceThicknessRange=[100,400]`。落地时按锁定版本 API 写代码，不照抄最新版文档中的新属性。[r185 材质源码](https://raw.githubusercontent.com/mrdoob/three.js/r185/src/materials/MeshPhysicalMaterial.js)

**透明花瓣风险**：相互穿插的薄花瓣使用 `transparent=true`、DoubleSide 并不能自动正确排序；引擎按对象排序，通常不逐个三角形排序。主花自然/银模式尽量保持不透明曲面；晶体模式减少交叉重叠，控制花瓣分组、厚度与相机角度，旋转一周验收，必要时为近景单独设计渲染方式。普通 alphaTest 只适合硬边裁切，不等同于柔和透光花瓣。[Three.js 透明处理说明](https://threejs.org/manual/pages/transparency.html)

**水面先做可交互的可信近似**：点击/轻扫记录少量波源，解析衰减圆波或小尺寸高度场驱动法线；使用 Fresnel 反射混合、浅水底色和低成本平面反射。明亮水纹/焦散可先以程序投影或烘焙纹理随波相位移动，必须在实现说明里称为“焦散视觉近似”，不宣称真实光子或路径追踪焦散。晶体花的透射不自动替周围水面生成物理正确焦散。仅在几何和视觉收益足够时考虑更完整求解。

明场和暗场维持同一个世界状态与相机连续性，逐渐改变背景、光比、表面显现和点云占比。暗场的上粉下蓝可由稳定的物体空间高度或采样颜色产生，再随解谜状态变化；不要按每帧屏幕坐标随机换色。

先保证有意图的构图与三维材质，再加特效：主花的轮廓和前中后景分离、柔和主光与侧逆光、主花/背景明度差、稳定的色彩管理、运动的收放。曝光不能随随机高亮剧烈跳变。

色彩贴图如 baseColor/emissive 使用 sRGB 标注，法线与 roughness 等数据贴图不做颜色转换；光照、插值在 Linear-sRGB 进行。WebGL 后处理链在最终输出转换一次，使用 OutputPass，避免重复 gamma/tone mapping。[官方色彩管理](https://threejs.org/manual/pages/color-management.html)

Bloom 只让花芯、受激粒子等局部超过阈值；保留暗部与花瓣中间调。可学习 selective bloom 的分层合成，但双重场景渲染可能增加成本；若单一 HDR 阈值已足够，不必照搬额外一套 scene render。[官方 selective bloom 示例](https://raw.githubusercontent.com/mrdoob/three.js/r185/examples/webgl_postprocessing_unreal_bloom_selective.html)

景深用于主花近景、停靠或照片模式；移动和解谜时保留路径清晰。雾用于空间层次，先用深度雾与少量经过设计的光束；全屏体积雾、传输/折射、屏幕空间反射、长拖尾全部默认后置评估。半透明花瓣只覆盖必要区域，优先使用可正确写深度的结构，避免整屏多层透明叠加。

## 7. 初始性能与内容预算

以下数字是工程起点。尚未指定目标硬件，且本次没有运行新作，因此不得写成“保证 60 FPS”。先在拟支持的集成显卡、桌面独显和一台实际手机上记录分辨率、DPR、浏览器、GPU、帧时间，再调整。

| 项目 | 轻量起点 | 标准起点 | 高档试验上限 |
|---|---:|---:|---:|
| 主体细粒子 | 8,192–16,384，无状态形变 | 约 60K 有效点，256²=65,536 状态槽 | 约 240K 有效点，512²=262,144 状态槽 |
| 主花几何 | 少量真实曲面；先以一朵六瓣百合为基准 | 同样的可读主花结构，提高曲面与法线细节 | 同左，提高近景材质与曲面细节；不靠堆花瓣数冒充品质 |
| 额外漂移花瓣/种子实例 | 200–500 | 500–1,500 | 2,000–3,000，需审查透明覆盖 |
| 主要渲染像素 | 约 0.5–0.9 MP | 约 0.9–1.4 MP | 约 2.1 MP；不盲目按屏幕原始 DPR |
| 帧时间目标 | p95 ≤ 33.3 ms | p95 ≤ 16.7 ms | 同标准；未达标则降级 |
| Bloom | 关闭或四分之一尺寸 | 半尺寸 | 半尺寸起，再评估 |
| 阴影/景深 | 无动态阴影、无景深 | 一盏受控阴影灯；只在停靠景深 | 同左，先保障主体运动 |
| 晶体/水面 | 低成本环境反射近似；保留材质区别 | 主花有限透射、半尺寸水面反射候选 | 试验色散与更完整反射；未达标即关闭 |

“约 240K”只是针对参考画面标签设置的高档压力测试目标，不是已测性能、更不是入门设备必须达到的数量；标准档约 60K 先保证连续形态和交互。纹理里的未使用槽仍可能消耗模拟成本，应计入预算。

附加初始目标：主体粒子每种材质/层级尽量一个 draw call；全场景主要 draw calls 先压到约 100 内，再根据测量调整。首章总传输资源争取 8–15 MB 内，其中首次可操作起点所需压缩资源≤8 MB，余下沿路线预取，后续区域按需载入；首屏壳和交互说明先出现。这些是产品目标，不是当前资源实际大小。精细档先以120K起步，240K只作压力测试；轻量档8–16K起步，有余量再试30K。最终产品预算以[设计提案第9节](design-proposal.md)及后续真实设备记录为准。

**计算显存，不只数粒子。** `position` 与 `velocity` 各两份 RGBA32F render target，合计 `64 × N` 字节：65,536 粒子约 4 MiB，262,144 粒子约 16 MiB。另加两份 RGBA32F 目标点纹理约 2 / 8 MiB；尚未包含初始化纹理、元数据、CPU 数组、网格、深度、后处理缓冲与纹理。单个 1920×1080 RGBA16F 颜色缓冲就约 15.8 MiB。大量后处理缓冲和透明覆盖可能比模拟本身更昂贵。

按 5 秒以上持续帧时间进行降级，使用迟滞与冷却，避免画质反复跳变。顺序建议：降低渲染比例 → 降低 bloom 分辨率/去掉景深 → 降透明覆盖与实体花瓣细节 → 在安全阶段切换更低模拟规模。只少画粒子但仍计算完整大纹理，不会获得相同的模拟性能收益。

## 8. 建议模块与首个验证切片

模块按职责分离：`app/` 管理启动和生命周期；`render/` 管理相机、灯光、色彩和质量；`particles/` 管理固定 ID、目标形态、模拟后端和材质；`world/` 管理空间与碰撞；`game/` 管理离散规则与存档；`audio/` 只响应游戏事件；`ui/` 管理介绍、设置、输入提示和可访问状态。界面不暴露给玩家无用的后端技术名词。

建议首个切片按以下顺序验证，避免先堆场景再发现主体效果不成立：

1. **连续性**：一朵原创花，固定 ID，分解—流动—重组，全程可绕视观察；没有整层跳切、重播重置或粒子突然换色。
2. **交互因果**：移动、水纹/追光和作用场改变空间状态，玩家至少有一次需要调整策略的行为；成功真的改变可通行空间。
3. **品质**：关掉 bloom 仍能看出花瓣材质、轮廓、层次；重新开启后增强局部光感，不能靠过曝掩盖几何不足。
4. **降级等价**：轻量模式保留目标、交互、反馈与通关条件；测试浮点模拟失败、丢失上下文、暂停、后台返回和存档被拒绝。
5. **完整小旅程**：入场教学、探索、发现、一次失败再尝试、聚合高潮、结束与可重玩，全部在同一个三维世界中发生。

验证需包括真实浏览器手动观察和可重复脚本。记录稳定阶段的 median/p95、最坏变形段、资源峰值估算、控制延迟与 console 错误；首次 shader 编译/资源解码与稳定帧数据分别统计。视觉核查至少覆盖侧面、背面、近景和低画质；截图漂亮不能证明连续动作和空间玩法成立。

## 9. 结论与未核实项

零素材采购与零付费生成调用能够成立，关键工具与环境资源都有明确免费路线。核心成本在原创主花、连续形态映射、运动设计、玩法关卡和真实设备调优。现工程有可参考的中性机制，但新作的内容、核心模拟和任务结构应独立。

尚待主任务确认或实测：最终平台与目标硬件；主花造型与玩家身份；采用的具体素材版本；WebGPU 是否值得成为主线；各档实际帧率、加载耗时与内存。任何标注“目标”“建议”“起点”的数字都不能替代这些验证。
