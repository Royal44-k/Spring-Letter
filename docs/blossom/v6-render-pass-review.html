V6 渲染通道复核：阴影归属与实测边界

2026-11-19。候选F的长时测试出现真实帧数不足后，团队先保留失败，再检查渲染链路。候选G仅让环境遮蔽的法线通道暂时停止更新共享阴影图；正式场景仍逐帧更新阴影。 这项修改有源码与绘制量证据，但三轮短实验不能支持“帧率翻倍”或“长时性能已修复”的结论。

本页对应本地锁定的 Three.js 0.185.0。候选F入口为 /assets/index-BXu5N06Q.js；G及独立修复实验入口为 /assets/index-BAJMaxNn.js，共用样式 /assets/index-B12KydA1.css。下文保留实验当时的端口与版本，不把后来同端口的构建当成原实验对象。

本地调用链与错误的阴影覆盖

  1. main.js的正式后期顺序为 RenderPass → GardenDepthPass → UnrealBloomPass → OutputPass。水面反射在 composer.render() 前更新。
  2. GardenDepthPass为获得接触深度，暂时隐藏传输系数大于0.1、低不透明度、关闭深度写入或标为排除的网格。这是为了不让透明花、水和天空形成不合适的实心遮蔽。
  3. 本地GTAOPass的 render() 调用 _overrideVisibility()、_renderOverride()；后者设定 scene.overrideMaterial 后再次执行 renderer.render(scene, camera)。替换为法线材质并不自动关闭阴影渲染。
  4. WebGLRenderer在绘制场景前调用 shadowMap.render()；WebGLShadowMap仅在 autoUpdate 与 needsUpdate 同时为 false 时跳过整张阴影更新。它遍历实际物体的 material 和可见性，不因 scene.overrideMaterial 是法线材质而停止。
  5. botany.js的花体网格本身会投影，main又为整个花束开启投影。晶花与琥珀花在AO通道被隐藏后，这次冗余阴影会把共享纹理改写为缺少这些投影物体的场景。它不仅重复工作，还改变了共享资源的内容。
  6. 本地Reflector在反射绘制时临时关闭阴影自动更新；本作水面反射下一帧因此可读取上一帧AO留下的不完整阴影。修复后，反射继续使用上一帧正式场景的完整阴影；原有一帧时序没有新增延迟。

这不意味着旧F的每个画面都明显错误：遮蔽是否启用、材料、投影位置和镜头都会影响可见差别。也不能要求修复前后逐像素完全相同；透明花相关的反射阴影允许出现正确性变化。

G采用的保护范围

在 GardenDepthPass.render() 保存 renderer.shadowMap.autoUpdate 与 needsUpdate，仅在调用 super.render() 的 try 中把二者置为false，finally首先恢复两个原值，再恢复可见性、覆盖材质与渲染目标。显式待更新请求不会被AO消费或吞掉。

正式RenderPass的逐帧阴影、1536²阴影尺寸、花体几何、材质、AO分辨率和后期参数保持原有设置。本项目没有发现会在AO渲染回调中重新设置 shadowMap.needsUpdate 的逻辑；该判断基于本轮本地源码检索，不外推任意插件场景。

双标志与异常恢复测试检查两标志的不同初始组合和异常路径；既有恢复测试继续覆盖场景状态恢复。该修正阶段CPU检查166/166通过；加入发行与媒体工具反例后，最终全量Node输出为178/178。CPU断言证明状态契约，不代替实际GPU画面与长时性能验收。

三轮短实验：全部数据

实验脚本与原始JSON保留全部三轮。Edge无头、1440×900，每轮新浏览器上下文，同机串行执行；每个状态先等待2.5秒，再采样约7秒，读取本作连续帧计数和帧间隔。实际经过百合/月银、莲/琥珀、大丽/流晶和回到行走状态，均为普通界面输入。

实验顺序是F、修复、修复重测，没有交替反转顺序，也没有清除驱动缓存或记录独立GPU计时器。renderer只返回 WebKit WebGL，不能据此断言具体硬件后端。帧间隔包含浏览器调度等因素，不能直接视为GPU耗时；绘制次数与三角形数是采样末帧的计数。

F长时失败、中断与G完整长跑

  • F第一次长时测试明确 passed: false：莲/月银的5.5秒稳态窗口只取得26个新帧，低于41帧门槛。保留原始失败，不改阈值来制造通过。
  • F第二次诊断记录由根任务主动中断，以转入隔离渲染实验。原始文件有89段已记录阶段，末段为第4轮莲/流晶、运行后771,596ms（约12.86分钟）；没有最终通过标记，也没有达到45分钟。它是约13分钟的未完成记录，不是失败后自动变为通过。
  • G已经固定构建，主路11项、取消6项、移动端10项与首花离开近景专项有同版报告；恢复后另完成三支线9项与雨潮8项。上次G保留内容中断的部分截图继续保存，不计通过。G界面11项已通过，确认实际全屏、双指接管、设置暂停/恢复、四形五系列与衣橱重载；其首次破开12.736秒/763帧/最大18.1ms仍只是单周期观察。
  • G长跑现已完成47.004分钟、13轮、351阶段，10项检查通过且错误为空。81组暖机后同状态资源比较最大增长0；稳态窗口最少144个新帧，稳态最大单帧间隔50.5ms、各段P95最高33.6ms，切换窗口最大183.6ms。这个结果来自同一台机器和这套普通输入序列，不证明所有设备稳定，也不把资源计数等同显存测量。
  • 后续G连续实录6项通过，媒体解码覆盖4397帧、1440×900、175.84秒末帧、0损坏帧；发行包实际解压和本机HTTP全量核对均绑定同一G构建。无声录像与录制开销不用于音质或稳定帧率结论。图文页面浏览器检查也已通过桌面/窄屏6组，截图另经人工查看；文档检查不外推游戏GPU性能。

本次长跑据完整G报告关闭，F失败与中断原样保留。后续判断仍应同时包含同构建身份、普通输入可达性、足量新帧样本、稳态资源数量及实际画面；若其他设备或更长序列失败，继续记录定位，不把此次通过描述成全部性能问题已经解决。
